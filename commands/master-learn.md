You are the MASTER SESSION (incumbent or just-retired) and the owner has asked you to
extract this campaign's learnings and improve the Master Session skill with them. This is
a curation task, not a diary: the skill must get SHARPER, not longer. Follow the steps in
order.

## 1. Mine — errors first, then patterns

Re-read the campaign's evidence in this order (the order biases you toward what actually
happened rather than what you remember):

1. **The ledger's error entries** — every entry attributed to a station (master's own
   errors FIRST; a learning motion that skips the master's mistakes teaches children to
   hide theirs).
2. **Child-reported process failures** and the countermeasures they adopted (these arrive
   pre-distilled — a child that wrote "structural, not attentional" did half your work).
3. **Rulings that got corrected** — every place a child refuted a master premise, a
   ratified plan, or a reviewer finding by measurement.
4. **Repetition** — anything that happened twice or more (in one child, across children,
   or across campaigns via the skill's existing parentheticals) is structural by
   definition and the strongest candidate.
5. Only then: novel patterns that WORKED (new protocol shapes, instruments, message
   forms) — success teaches less than failure and earns inclusion only with a concrete
   incident attached.

## 2. Sort — three buckets, strict

For each candidate lesson, ask: "would this have changed a decision in a DIFFERENT
campaign?" Sort into:

- **Skill-worthy** — generalizes beyond this codebase/tooling; names a failure mode any
  master fleet can hit. Goes into the skill.
- **Project-worthy** — true here, tied to this repo's tools or layout. Goes into project
  memory / AGENTS.md territory, NOT the skill. Say where you routed it.
- **Already covered** — the skill states it. If the campaign produced a SHARPER incident
  or a mechanical countermeasure the existing rule lacks, upgrade the rule's
  parenthetical; otherwise leave it alone and count it as validation, not news.

## 3. Fold — edit the skill like the skill edits itself

- Every rule you add follows the house form: **bold imperative claim**, mechanism in one
  or two sentences, then the concrete incident in parentheses — a trap list that names
  nothing prevents nothing.
- Prefer UPGRADING an existing rule over adding a sibling; prefer a new reference file
  over bloating SKILL.md when the material is a protocol (multi-step, with instruments)
  rather than a rule.
- Wire it in: new reference files get a line in the References section; new commands get
  a line in Companion commands.
- Countermeasures must be MECHANICAL where the failure was structural (a preflight
  command, a read-back diff, an ordering rule) — "be more careful" is not a learning.

## 4. Report — what changed and what didn't

Tell the owner, in this shape:

- **Added** — each new rule/reference with its one-line lesson and the incident that paid
  for it.
- **Upgraded** — existing rules that got a sharper incident or countermeasure.
- **Validated** — rules the campaign stress-tested that held as written (this is the
  skill's regression suite; say which).
- **Routed elsewhere** — project-specific lessons and where they went.
- **Rejected** — candidates you deliberately left out and why (one line each; the owner
  may overrule).

Do NOT edit the skill's doctrine sections (authorization classes, hard-rule deletions)
without flagging the specific change to the owner first — adding is cheap, changing
meaning is a decision.
